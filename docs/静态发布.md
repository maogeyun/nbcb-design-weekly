# 静态发布

线上公开站继续使用现有 Direct Upload 项目 `nbcb-design-weekly` 和 `https://nbcb-design-weekly.pages.dev`。不要把该项目改成 Cloudflare 原生 Git 构建。GitHub Actions 使用官方 `cloudflare/wrangler-action` v4.1.3，只执行 `pages deploy static-site`。

2026-11-12 的故障是 Pages 在没有构建命令时发布了仓库根。部署 workflow 不上传仓库根、`web/`、后台、API 或 `store.json`。

## 当前快照

`static-site/static-data/manifest.json` 来自 2026-11-11 已发布产物：5 期、34 篇、138 个技能。它不是由 Git 里的 `web/data/store.json` 重新生成的。该 store 含 34 篇已发布文章和 157 篇候选稿，不能作为公开站数据源。

本地后台和 `web/data/` 保留。发布流程不删除这些文件。

`publish.config.json` 里的 `productionOnMainPush` 现在是 `false`。合并到 `main` 会跑校验，但生产上传任务保持跳过。

## 需要你配置的凭据

在仓库 Settings 中配置，不要写进提交或日志：

| 名称 | 类型 | 值 |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | Secret | 你的 Cloudflare API Token。此仓库不保存 token。 |
| `CLOUDFLARE_ACCOUNT_ID` | Variable，或 Secret | `4b6ab536e9d18ba3b4b438b475e3cf4e` |

Token 至少需要这个 Pages 项目的 Pages Edit 权限。workflow 只判断这两项是否非空，不打印内容。

## 验收顺序

`workflow_dispatch` 要等 workflow 进入默认分支后，Actions 页面才会出现 Run workflow。因此顺序是：

1. 合并本 PR。合并触发的 `pages-deploy` 会校验快照；`production-upload` 因闸门关闭而跳过，正式站不变。
2. 在 Actions 打开 `pages-deploy`，Branch 选择一条非 `main` 且含这份 `static-site` 的分支，target 选 `preview`。分支名里的 `/` 会变成 `-`。
3. 打开日志里的 `alias_url`。确认首页、期刊、文章、技能、PDF 和 `/m/` 能打开，`/admin`、`/api`、`/web/data/store.json` 打不开，清单仍是 5/34/138。
4. 预览通过后，在 `main` 上手动运行 workflow：target 选 `production`，confirm 填写 `publish-production`。这一步才更新正式 URL。
5. 如果之后希望 `main` 的普通 push 自动发生产，另开一个小 PR，只把 `productionOnMainPush` 改为 `true`。在此之前不要改它。

手动生产如果漏填 `publish-production`，workflow 会失败且不上传。

## Fork PR

`pages-publish-check` 会在 pull request 上运行，其中没有 `secrets` 引用。`pages-deploy` 没有 `pull_request` 触发器。fork 不能手动派发本仓库的 workflow，也不能向 `main` push。因此 fork PR 取不到 `CLOUDFLARE_API_TOKEN`。`node scripts/check-pages-workflows.mjs` 会在 CI 里检查这些约束。

## 以后从本地同步新内容

在持有最新已发布数据的电脑上操作。不要在 GitHub Actions 里运行 `npm run build:static`。

1. 本地后台确认内容已发布。
2. 生成快照：

   ```bash
   cd web
   npm run build:static
   ```

3. 在仓库根校验，失败就不要提交：

   ```bash
   node scripts/verify-pages-publish.mjs
   node scripts/check-pages-workflows.mjs
   ```

4. 提交 `static-site/` 和确实需要的发布配置。不要把 `.env`、后台数据或 token 放进 `static-site/`。
5. 开 Pull Request，等无 secret 的 `pages-publish-check` 通过。
6. 合并后先按上面的 preview 验收，再决定是否手动发生产。自动生产仍由 `productionOnMainPush` 控制。
